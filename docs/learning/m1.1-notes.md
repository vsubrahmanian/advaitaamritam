# Why we need a Python .venv?

Because we're going to install Python packages for Advaitaamritam, and a **virtual environment keeps this project's dependencies isolated from the rest of your Mac**.

Think of it like a separate toolbox for this project.

### Without a virtual environment

If you do:

```bash
pip install openai
```

the package can end up in your system/global Python environment.

Later you might have:

```text
Project A → openai 1.x
Project B → openai 2.x
Project C → some other package version
```

and their dependencies can conflict.

### With `.venv`

You get:

```text
Your Mac
│
├── System Python
│
├── Other projects
│
└── advaitaamritam
     │
     └── .venv
          ├── Python packages
          ├── OpenAI SDK
          └── Project-specific dependencies
```

When you run:

```bash
source .venv/bin/activate
```

your terminal effectively says:

> "For this terminal session, use the Python environment belonging to Advaitaamritam."

Then:

```bash
pip install openai
```

installs it **inside `.venv`**, rather than globally.

### Why this matters for your learning project

We're deliberately building Advaitaamritam as something you'll keep evolving through:

**M1 → M2 → RAG → n8n → agents → etc.**

You'll accumulate packages such as:

```text
openai
supabase
python-dotenv
pydantic
...
```

The virtual environment keeps all of those dependencies belonging to this project.

### What about `.venv` in GitHub?

You **don't commit it**.

That's why we put:

```text
.venv/
```

in `.gitignore`.

Anyone cloning your GitHub repo creates their own environment from the project's dependency list.

---

### For M1.1

You only need to understand these two commands:

```bash
python3 -m venv .venv
```

**Create** the isolated environment.

```bash
source .venv/bin/activate
```

**Enter/use** that environment.

You'll know it's active when your terminal shows something like:

```text
(.venv) your-mac:advaitaamritam$
```

When you're done:

```bash
deactivate
```

**This is not strictly required to make an API call.** It's a Python development best practice, and I'm recommending it because we're building a project that will grow rather than a one-off script.
